# 中級 Rust コードリーディング教材の設計

## 目的と到達点

Rust Book を一通り読んだ学習者が、所有権・型・trait・非同期処理の組み合わさった Rust コードを読み解ける教材へ発展させる。読書記録 API を題材とし、完成形の実装、テスト、ドキュメントだけで学習が完結する構成にする。

読了時には、次の内容をコードを根拠に説明できることを目指す。

- 型シグネチャから、所有する値、借用する値、返り値、失敗の種類を読み取れる。
- newtype、可視性、型状態がそれぞれ何を保証するか説明できる。
- trait の契約と具体実装を区別し、ジェネリックな service がどこで具体化されるか追える。
- 実行時に分かる状態を、状態ごとの型へ接続する処理を読める。
- `.await` をまたぐ借用と、返される `Future` の `Send` 制約を説明できる。
- 単体テスト、フェイク、実 DB、HTTP 統合テストが保証する範囲を区別できる。

## 教材の方針

- 一つの完成した API を、複数の観点から段階的に読む。
- 変更前の実装や Git の履歴を読むことを前提にしない。Before/After 比較を教材の軸にしない。
- Rust とアーキテクチャの深さ、教材としての体験と構成を優先する。
- 実務寄りの機能追加は対象外とする。認証、外部 API、検索、ページネーション、バックグラウンド処理などを学習項目のために追加しない。
- 独自 Future の実装、`Poll`、`Pin`、独自 Tower middleware には踏み込まない。
- 60〜90 分に全内容を収める制約は設けない。第1部を60〜90分、全体を3〜5時間程度と仮置きし、実際の読解量に応じて調整する。

本書は、2026-08-28 の設計を発展させるための仕様である。実装後の教材への入口は README と mdBook とし、過去の設計書を学習の前提にしない。

## API と読書状態の規則

既存の本の登録・一覧・詳細取得・状態変更・メモ追加・削除を題材として使う。HTTP の状態名と DB の保存値は `want_to_read`、`reading`、`finished` とする。

新しい本は必ず未読で登録する。許可する状態変更は次の2つに限定する。

```text
WantToRead → Reading → Finished
```

| 条件 | HTTP 応答 |
| --- | --- |
| 未読から読書中、読書中から読了への変更 | `200 OK` |
| 状態の飛び越し、逆戻り、同じ状態への更新 | `409 Conflict` |
| 認識できない状態名 | `400 Bad Request` |
| 存在しない本への、有効な状態名による更新要求 | `404 Not Found` |
| 取得後、保存前に別の更新が成立していた場合 | `409 Conflict` |

入力の状態名を検証してから対象を取得する。型へ変換できない JSON や Path など、handler 到達前の失敗には引き続き Axum の rejection を使う。アプリケーションのエラーは既存の JSON エラー形式にそろえ、競合のコードとして `conflict` を追加する。DB 内の不正な値や内部 DB エラーは `500 Internal Server Error` とし、内部の詳細を HTTP 応答へ露出しない。

## ドメインの型設計

### 検証済みの値

タイトル、著者、メモ本文を、それぞれ検証済み newtype とする。既存の前後空白の除去と空文字拒否を構築時の規則としてまとめる。

- 内部の文字列は非公開にし、検証を経由して構築する。
- `TryFrom` による失敗し得る構築と、読み取り用の借用を提供する。
- HTTP 入力の不正と DB に保存された不正値は、境界で別のエラーとして扱う。
- `BookId` と `NoteId` による ID の区別を保つ。
- HTTP の DTO、DB の行、ドメイン型を区別する。外部表現からの復元が型の保証を迂回しないようにする。

### 型状態による本の表現

本を `Book<S>` とし、状態マーカーとして `WantToRead`、`Reading`、`Finished` を使う。状態マーカーの値を保持する構成とし、この表現のために `PhantomData` を導入しない。

```rust
impl Book<WantToRead> {
    pub fn start_reading(self) -> Book<Reading> { /* 実装 */ }
}

impl Book<Reading> {
    pub fn finish(self) -> Book<Finished> { /* 実装 */ }
}
```

遷移は `self` を消費し、次の状態の本を返す。任意の状態へ変更する公開 setter や、任意の状態の本を作れる汎用の公開コンストラクタは設けない。共通情報と状態のフィールドを非公開にし、型状態の保証を守る。

DB から既存の本を復元する経路は、利用者が新しい本を作る経路と区別する。復元は信頼境界の内部に限定し、保存値の検証を経て行う。

### 実行時の状態との接続

DB の状態は実行時に判明するため、取得した本は次の enum で表す。

```rust
enum StoredBook {
    WantToRead(Book<WantToRead>),
    Reading(Book<Reading>),
    Finished(Book<Finished>),
}
```

service は現在の `StoredBook` と要求された `ReadingStatus` を照合し、有効な組み合わせでのみ遷移メソッドを呼ぶ。

`ReadingStatus` は HTTP 入力、一覧の絞り込み、保存値などの動的な表現として残す。型状態で実行時の判定が不要になるとは説明しない。判定後の操作を型で制限することが、型状態の担当範囲である。

## レイヤーと依存関係

```text
Router / AppState
    ↓
handler：HTTP の入力・出力
    ↓
ReadingService<R>：検証とユースケース
    ↓ R: BookRepository
SQLite の repository 実装：SQL とドメイン型の変換
    ↓
SQLite
```

テストでは、同じ `ReadingService<R>` にフェイク実装を渡す。

| 要素 | 責務 |
| --- | --- |
| `main` / `app` | DB、repository、service、Router の組み立てと共有状態 |
| `handler` | extractor、入力 DTO、service 呼び出し、出力 DTO |
| `service` | 入力規則の適用、対象取得、遷移の選択、保存の依頼 |
| `domain` | 検証済みの値、ID、型状態、動的な状態の表現 |
| repository trait | service が必要とする操作と失敗時の契約 |
| SQLite repository | SQL、行の復元、条件付き更新 |
| `error` | アプリケーションエラーと HTTP 応答への変換 |

既存のモジュール責務を足場に、trait と具体実装を読み分けやすい配置にする。型やモジュールの公開範囲は、アプリケーションの組み立てと教材の doctest に必要な範囲に限定する。

### repository trait と非同期処理

- `BookRepository` が既存のユースケースで必要な永続化操作を表す。
- `ReadingService<R>` は具体的な SQLite 型や SQL に依存しない。
- 起動時に SQLite 実装を渡し、テスト時にフェイクを渡す静的ディスパッチを使う。
- 非同期メソッドが返す `Future` には、Axum の handler から利用するために必要な `Send` 制約を明示する。`impl Future<Output = ...> + Send` を返す trait メソッドと、具体実装の非同期処理を接続して説明する。
- 共有状態と repository の型には、利用箇所から必要になる境界を設定する。`Send`、`Sync`、`Clone`、`'static` を理由なく一律に付与しない。
- 関連型は `TryFrom::Error` など実際に使う箇所で扱う。学習項目を増やすためだけの抽象化は追加しない。

### 状態保存と競合

型状態はメモリ上の操作を制限するが、別リクエストによる DB 更新を防がない。状態保存は ID と変更前の状態を条件に含む単一の更新文で行う。

- 更新できた場合だけ成功とする。
- 対象取得時の未検出は `404` とする。
- 対象を取得できた後に条件付き更新が成立しなかった場合は、途中での削除も含めて `409` とする。
- フェイクも条件付き更新の契約を満たす。SQLite 固有の挙動は実 DB のテストで確認する。

型による保証と DB による保証の境界を、同じ状態更新の読解経路で説明する。

## mdBook の構成

README は概要、起動方法、API 一覧、ファイル構成、検証コマンド、教材へのリンクを載せる入口とする。詳細な読解ガイドは `docs/book/` に置き、ルートの `book.toml` から参照する。

| 部 | 章の題材 | 到達点 |
| --- | --- | --- |
| 導入 | 前提知識、起動、読み方、全体図 | アプリを動かし、モジュールの役割を把握する |
| 第1部：処理を端から端まで追う | 依存関係の組み立て、本の登録、詳細取得とエラー | HTTP から DB、応答まで値と呼び出しを追う |
| 第2部：型でルールを表現する | 検証済み newtype、`Book<S>`、動的な境界 | 型の保証と実行時の判定を区別する |
| 第3部：抽象化と非同期を読む | repository trait、`ReadingService<R>`、借用、`Future`、`Send` | 型の具体化と非同期処理の制約を説明する |
| 第4部：テストから保証を読む | フェイク、SQLite、更新競合、Router | 各テストの実行範囲と保証を説明する |

第1部でも完成形のコードを使う。型状態やジェネリクスは役割を先に説明し、後の部で定義と制約を深掘りする。

各章は次の形式にそろえる。

1. この章で答える問い
2. 読むファイル、型、関数と読む順序
3. 型シグネチャ、値の移動、呼び出し先を追う解説
4. コードを根拠に答える理解の確認
5. 自習のための解答・解説

重要なコード抜粋は `{{#include ...}}` と必要に応じたソース内アンカーで実装を参照する。行番号への依存や、実装コードの手動複製を避ける。

Mermaid で処理経路、依存関係の組み立て、状態遷移、DB から型への変換境界を図示する。

### ツールと配信

- mdBook と、badboy 氏によるオリジナルの `mdbook-mermaid` を使う。
- mise でツールを管理し、実装時に互換性を確認したバージョンを固定する。
- Mermaid は JavaScript を book に同梱し、閲覧側で描画する方式を使う。Node.js やヘッドレスブラウザをビルドの必須依存にしない。
- `mdbook serve` でローカル閲覧する。HTML の公開基盤は今回の対象に含めない。
- 生成 HTML は Git 管理対象外とする。Mermaid の配信用資産はプラグインの導入方式に合わせて配置し、オフラインでも図が描画できる構成にする。

## テストと受け入れ条件

| 検証 | 確認する内容 |
| --- | --- |
| newtype の単体テスト | 空白の正規化と空文字の拒否 |
| 型状態の単体テスト | 許可された遷移と、共通情報の保持 |
| `compile_fail` doctest | 未読からの直接読了など、許可されない操作を呼べないこと |
| フェイクによる service テスト | 遷移の許可・拒否、未検出、保存時の競合や失敗 |
| SQLite のテスト | 行の復元、不正な保存値、永続化、条件付き更新 |
| Router の統合テスト | 既存 API と、新しい遷移規則・HTTP エラー |
| mdBook のビルドと表示確認 | 章構成、ソースの取り込み、リンク、Mermaid の描画 |

`compile_fail` の例は、公開された型を正しく参照したうえで、意図した不正操作によって失敗するようにする。対応する有効な操作がコンパイルできる例も確認し、単に型の非公開や import の誤りで失敗する教材にしない。

競合テストは待ち時間に依存させず、同じ変更前状態を使う更新を制御して、後の更新が拒否されることを確認する。型による制約と永続化の契約の両方を検証する。

実装後の基本検証コマンドは次のとおりとする。

```bash
cargo fmt -- --check
cargo test
cargo clippy --all-targets --all-features -- -D warnings
mdbook build
```

加えて `mdbook serve` で目次、章移動、検索、コード抜粋、Mermaid の描画を確認する。ビルドが通ったことだけを、ブラウザ表示の確認として扱わない。

## 実装の進め方

1. 本書のレビュー後、実装計画を作る。
2. 検証済み newtype、型状態、repository trait、service、SQLite 実装を一つの完成形として接続する。
3. テストで型の保証と実行時の契約を確認する。
4. mdBook の各章を完成形のコードへ接続し、README を入口として整理する。
5. コードの検証、教材のビルド、表示と読解導線を確認する。

章の問いと到達点は実装中も参照する。コードを完成させてから説明を付け足すのではなく、各概念を読める場所が実装にあることを確認しながら進める。
