# 一括読了記録を小さな値から並行処理まで段階的に読む

教材は言語機能ごとの独立した説明ではなく、一括読了記録という一つの完成形を徐々に広げて読む構成にする。Rust Book 読了直後の読者が、入力の一項目から一冊の状態変化と保存へ進み、その理解を使って複数の Future の進行、失敗、終了を説明できる順序を採る。

## 各章の共通構成

各章には、問い、必要な前提、読む対象と順序、完成形からの短いコード抜粋、理由を追う解説、成立する別案または成立しない別案、確認問題、実装上の根拠を示す解答を置く。コード編集や実行を修了条件にせず、本文と参照コードだけで問いへ答えられるようにする。

本編は完成形だけを示す。移行途中の実装や旧構成を学習順序として残さない。別案は比較に必要な最小の断片とし、本編の実装と見分けられるようにする。

## 確定した章立て

| --- | --- | --- | --- |

| 第 1 部：一件の値を整える | 要求から検証済みの入力へ | `String` と一覧の所有権はどこへ移り、保存前に何を検査するか | 導入 |
| 第 1 部：一件の値を整える | 借用して検査し、所有して渡す | 検査だけなら借用で足り、Future へ渡す値を所有する必要があるのはなぜか | 要求から検証済みの入力へ |
| 第 2 部：一冊の読了を成立させる | 保存状態を型状態へ接続する | DB 由来の状態をどう検査し、なぜ `Book<Reading>` だけが読了へ進めるか | 第 1 部 |
| 第 2 部：一冊の読了を成立させる | 状態変更とメモを一緒に保存する | 型状態だけでは足りない保証を、条件付き更新と transaction がどう補うか | 保存状態を型状態へ接続する |
| 第 2 部：一冊の読了を成立させる | 失敗後に何が残るか | 入力不正、未検出、状態競合、依存先の失敗で保存結果はどう違うか | 状態変更とメモを一緒に保存する |
| 第 3 部：Interface の向こうを読む | `BookRepository` の契約 | 呼び出し側が知る必要のある不変条件と失敗を、どこまで小さい Interface に置けるか | 第 2 部 |
| 第 3 部：Interface の向こうを読む | フェイクと SQLite Adapter | 同じ契約を二つの Adapter がどう満たし、具体型はどこで決まるか | `BookRepository` の契約 |
| 第 4 部：複数の処理を進める | Future が値を保持する範囲 | 一冊の Future は何を所有し、何を借用して `.await` をまたぐか | 第 1〜3 部 |
| 第 4 部：複数の処理を進める | 独立した読了記録を並行に進める | 逐次待機せず複数を進める理由と、同時に進める上限は何か | Future が値を保持する範囲 |
| 第 4 部：複数の処理を進める | 完了順と入力順を分ける | 異なる順序で完了した結果を、どの所有値で入力へ対応付けるか | 独立した読了記録を並行に進める |
| 第 4 部：複数の処理を進める | 失敗と親 Future の終了 | 一件の失敗後に何を続け、親の終了時に未完了処理と保存済み結果はどうなるか | 完了順と入力順を分ける |
| 第 5 部：利用者の経路を読み直す | HTTP から SQLite まで | Router、handler、service、repository、SQLite を値と失敗がどう往復するか | 第 1〜4 部 |
| 第 5 部：利用者の経路を読み直す | 検証の保証と限界 | 型検査、フェイク、SQLite、Router、実アプリの確認はそれぞれ何を示すか | HTTP から SQLite まで |

Axum、Tokio、SQLx の制約は、アプリ側で要求元を説明するために必要な公開 Interface だけを、`Cargo.lock` で固定された対象バージョンとともに読む。ライブラリ内部の網羅的な読解には広げない。

## 学習目標と実処理の対応

| 学習目標 | 対応する章 | 実処理と交わる制約 | 比較する別案 | 読者が答える問い | 主な検証 |
| --- | --- | --- | --- | --- | --- |
| 所有権、部分的な移動、借用 | 「要求から検証済みの入力へ」「借用して検査し、所有して渡す」「Future が値を保持する範囲」 | HTTP の `items` を検証し、一冊分の所有値を子 Future へ渡す | 全入力の clone、参照を切り離した task へ渡す案 | どの Future が本文と入力位置を所有し、どの呼び出しだけが借りるか | コンパイラ、値変換の振る舞い |
| 型の保証と実行時検査 | 「要求から検証済みの入力へ」「保存状態を型状態へ接続する」 | `NoteBody`、`Book<Reading>`、保存済み状態、重複と件数 | 文字列と状態名を最後までそのまま扱う案 | 型が防ぐ不正と、DB や要求全体に対して実行時に調べる不正は何か | doctest、Router と SQLite |
| 状態変化と保存 | 「保存状態を型状態へ接続する」「状態変更とメモを一緒に保存する」 | 読書中から読了への遷移、条件付き更新、メモ追加 | 型状態だけに任せる案、更新後に別途メモを保存する案 | 合法な `Book<Finished>` があっても保存を拒否する場合は何か | SQLite Adapter、Router と SQLite |
| 原子性と部分成功 | 「状態変更とメモを一緒に保存する」「失敗後に何が残るか」 | 一冊では transaction、冊子間では独立 | 全冊を一 transaction にする案、二つの SQL を別々に確定する案 | 何を一緒に戻し、何を別の成功として残すか | 失敗注入後の保存状態 |
| Module、Interface、Adapter | 「`BookRepository` の契約」「フェイクと SQLite Adapter」 | `BookRepository` に原子的な保存契約を置き、SQLite とフェイクが満たす | service が SQLx transaction を扱う案、テスト専用 trait | 呼び出し側が知るべき契約と Adapter 内へ隠す詳細は何か | 二つの Adapter に対する同じ観測 |
| Future、`Send`、`Sync`、有効期間 | 「Future が値を保持する範囲」 | 親 Future が子 Future を所有し、共有 repository を借用する | `tokio::spawn` で切り離す案、全件逐次案 | `'static` が不要な理由と、共有借用に `Sync` が関係する理由は何か | コンパイラ、制御可能なフェイク |
| 並行性、順序、資源制約 | 「独立した読了記録を並行に進める」「完了順と入力順を分ける」 | 最大 8 件を並行に進め、位置を持って入力順へ戻す | 完了順で返す案、無制限に仕事を作る案 | 実行順を固定せずに結果の対応を固定するには何を所有するか | 待機点を持つフェイク |
| 失敗伝播と処理の寿命 | 「失敗後に何が残るか」「失敗と親 Future の終了」 | 一件の失敗後も継続し、親の破棄で未完了の子も破棄する | 最初の失敗で全件終了、background task を残す案 | 保存済みの結果と進行中の Future をなぜ同一視できないか | 失敗注入、親 Future の破棄 |
| 端から端の契約 | 「HTTP から SQLite まで」「検証の保証と限界」 | HTTP 応答、入力順の結果、再取得した本とメモ | 内部関数ごとのテストだけで済ませる案 | 利用者から確認できる保証と、内部の検証だけで分かる保証は何か | Router、実アプリ、ブラウザ、読解レビュー |

## 検証の配置

| 検証 | 確認すること | そこからは分からないこと |
| --- | --- | --- |
| 型検査と doctest | 合法な型状態の遷移、所有権、有効期間、`Send` などの条件 | 実際の poll 順、HTTP 応答、SQLite の保存結果 |
| service と制御可能なフェイク | 並行開始、完了順と入力順、失敗後の継続、親 Future の終了 | SQL、transaction、Axum の rejection |
| SQLite Adapter | 条件付き更新、状態変更とメモの commit・rollback | HTTP の status・JSON、service の結果整列 |
| Router と実 SQLite | 入力の受理・拒否、項目ごとの結果、再取得できる保存状態 | TCP 設定、任意の scheduler や障害 |
| 実アプリの実行 | 実際の server 経路で返る結果と保存状態 | 実行しなかった障害、将来の全実行 |
| mdBook のビルドとブラウザ確認 | 抜粋、図、章移動、確認問題、検索の表示 | 読者が問いへ答えられることそのもの |
| 読解レビュー | 本文と参照コードだけで各章の問いへ答えられるか | 任意の読者の理解、実装の実行時安全性 |

待ち時間の短さや偶然の task 順序で並行性を判定しない。制御可能な依存先で複数の処理が開始したことを観測してから解放する。実アプリの確認、ブラウザ表示、読解レビューは自動テストの成功で代用しない。

## 検討した別案

### 現在の言語機能別の部をそのまま拡張する

既存章を再利用しやすいが、読者が所有権、型、抽象化、非同期を別々の話として覚え、一つの処理で制約が交わる理由を追いにくい。完成形のユースケースを軸に再構成する。

### 最初から一括処理全体を追う

全体像は早く見えるが、Rust Book 読了直後の読者に HTTP、型状態、trait、transaction、複数 Future を同時に要求する。導入で完成形を短く見せたあと、一件の値と一冊の保存へ範囲を絞ってから広げる。

### 実行演習を必須にする

実行結果を自分で得る利点はあるが、環境準備を学習の前提にし、読む対象の根拠を教材だけで追えなくする。実行手順は任意の確認として残し、本文には観測済みの結果と保証の限界を示す。
