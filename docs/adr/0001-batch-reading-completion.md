# 読書記録 API に一括読了記録を加える

Rust Book 読了直後の学習者が、所有権、型による保証、実行時の状態、保存、失敗、複数の非同期処理を一つの実処理として追える題材が必要である。読書記録という既存の文脈と Axum・SQLx・SQLite を維持し、読書中の複数冊を読了時のメモとともに記録する「一括読了記録」を新しいユースケースとして加える。既存の概念を使って新しい振る舞いを作れるため、別の業務領域や外部サービスの説明を増やさずに学習目標へ集中できる。

## 対象読者と到達点

対象読者は Rust Book を一通り読み終えた直後で、Axum・SQLx・SQLite の開発経験は前提にしない。読了時には、完成した一括読了記録を根拠に次を説明できることを目標とする。

- HTTP の所有値が検証済みの値へ変わり、Future 間で移動または借用される場所
- `Book<Reading>` から `Book<Finished>` への遷移が保証することと、保存時に再検査すること
- 一冊の状態変更とメモ追加をまとめる保存単位と、冊子間の部分成功の違い
- `BookRepository` の Interface が SQLite Adapter と制御可能なフェイクの両方へ届く仕組み
- 独立した複数の Future を並行に進めても、入力と結果の対応を失わない仕組み
- 一件の失敗または親処理の終了後に、進行中の処理と保存済みの結果がどうなるか
- 型検査、実行テスト、実アプリの確認、読解レビューがそれぞれ保証する範囲

## 維持する題材と技術

| 対象 | 決定 | 理由 |
| --- | --- | --- |
| 題材 | 本、読書状態、メモを維持する | 一件の読了記録だけで検証済みの値、型状態、複数の保存、失敗を結び付けられる |
| Web | Axum を維持する | HTTP 入力と handler の Future を学ぶ既存の入口を再利用できる |
| 永続化 | SQLx と SQLite を維持する | trait の Adapter、非同期 I/O、条件付き更新、トランザクションを小さい環境で確認できる |
| 閲覧基盤 | mdBook、ソース取り込み、Mermaid を維持する | 学習目標に無関係な基盤移行を避け、完成形の実装と抜粋を対応付けられる |
| 外部サービス | 導入しない | 並行処理のためだけに認証、通信障害、秘密情報という別の前提を増やさない |

技術構成を維持するのは現状追認ではない。新しいユースケースが必要とする状態遷移、原子性、差し替え可能な Adapter、非同期処理を既存技術で表せるためである。外部 I/O の待ち時間や再試行そのものが学習目標になった場合は、外部サービスを持たないこの判断を再検討する。

## 利用者向け Interface

新しく `POST /reading-completions` を追加する。要求は `items` に 1 件以上 8 件以下の読了記録を入力順で持つ。

```json
{
  "items": [
    {"book_id": 12, "body": "所有権の章を実装と結び付けて読めた"},
    {"book_id": 7, "body": "Future が保持する値を確認した"}
  ]
}
```

要求全体の不変条件は次のとおりとする。

- `items` は 1 件以上 8 件以下である。
- 一つの要求内で `book_id` は重複しない。
- 各 `body` は前後の空白を除いたあとも空ではない。
- JSON の構造と上記の入力規則をすべて検査してから、保存処理を一つでも始める。

構造または入力規則が不正なら `400 Bad Request` と既存の `validation_error` 形式を返し、どの本も変更しない。Axum が handler より前に返す JSON extractor の rejection は、既存どおりアプリケーション共通のエラー JSON の対象外とする。

入力全体が正しければ、各本の読了記録を処理し、すべての読了結果を入力順で `200 OK` として返す。完了順は応答順に影響しない。

```json
{
  "results": [
    {
      "book_id": 12,
      "outcome": "completed",
      "book": {
        "id": 12,
        "title": "Programming Rust",
        "author": "Jim Blandy",
        "status": "finished"
      },
      "note": {"id": 31, "body": "所有権の章を実装と結び付けて読めた"}
    },
    {
      "book_id": 7,
      "outcome": "failed",
      "error": {"code": "conflict", "message": "reading state conflict"}
    }
  ]
}
```

入力が正しい要求では、一冊の失敗を要求全体の HTTP エラーに変えない。各失敗は対応する読了結果に `not_found`、`conflict`、`internal_error` のいずれかを持つ。DB の詳細や不正な保存値は `internal_error` の本文へ漏らさない。`207 Multi-Status` は WebDAV 由来の知識を増やす一方、この教材では項目ごとの結果を JSON で十分に区別できるため使わない。

## 一冊の状態変化

一冊の読了記録は、保存済みの本が処理時点で読書中の場合だけ成立する。

1. 本を取得する。存在しなければ `not_found` とする。
2. 保存値を検証済みの値と読書状態へ復元する。
3. 読書中でなければ `conflict` とする。
4. `Book<Reading>` の所有権を使って `Book<Finished>` を作る。
5. 保存時にも現在状態が読書中であることを条件に、読了への変更とメモ追加を一つの保存単位として確定する。

`Book<Finished>` は手元の値が合法な遷移で作られたことを保証するが、DB の現在状態、メモとの同時保存、別要求との競合は保証しない。これらは実行時の条件付き更新とトランザクションで保証する。

## 既存契約とデータ

次を変更しない。

- 本の登録、一覧、状態による絞り込み、詳細取得、状態変更、メモ追加、削除のパスと成功応答
- `WantToRead → Reading → Finished` だけを許す状態遷移
- 既存のアプリケーションエラーと、内部詳細を隠す方針
- `books` と `notes` の表、列、制約、および既存データ

一括読了記録は既存 Interface への追加であり、既存の状態変更やメモ追加の別名、互換層、旧形式を作らない。読了記録は独立した永続エンティティではなく、読了への状態変更と既存のメモを一緒に成立させる操作であるため、スキーマを増やさない。監査可能な読了履歴、再試行用の冪等性キー、読了の取り消しが必要になった場合は、別エンティティと migration が必要なのでこの判断を再検討する。

## 検討した別案

### 一括メモ追加

複数の本へメモを追加するだけなら並行処理は示せるが、型状態、状態競合、複数変更の原子性が一つの処理で交わらないため採用しない。

### 外部書誌サービスからの一括取り込み

独立した通信は並行処理の動機を作りやすい。一方で、認証、HTTP client、再試行、外部サービスの可用性が教材の前提になり、既存の状態遷移と保存の学習から焦点が外れるため採用しない。外部通信自体を到達点にするなら成立する案である。

### 一括読了記録を新しい表に保存する

履歴や冪等性を扱うなら成立する。しかし今回必要なのは読書中から読了への遷移とメモの原子的な保存であり、既存の `books` と `notes` で表現できる。用途のない永続概念を増やさない。
