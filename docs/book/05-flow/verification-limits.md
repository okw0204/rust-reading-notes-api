# 検証の保証と限界

## 問い

型検査、フェイク、SQLite、Router、実アプリ、ブラウザ確認、読解レビューは、それぞれ何を示し、何を示さないのでしょうか。

## 前提

[HTTP から SQLite まで](http-to-sqlite.md)を読み、一括読了記録の利用者向け経路を確認しているものとします。

## 読む場所と順序

1. `src/domain/book.rs` の doctest。
2. `src/service/tests.rs` の並行進行、失敗継続、親 Future 終了のテスト。
3. `src/repository/sqlite.rs` の repository テスト。
4. `tests/api.rs` の一括読了記録テスト。
5. `README.md` の実行手順と本章の検証表。

## 解説

| 検証 | 実際に通る範囲 | 分かること | 分からないこと |
| --- | --- | --- | --- |
| 型検査と doctest | 公開されたドメイン型、所有権、trait 境界 | 合法な遷移が書け、不正な遷移が意図した規則で拒否されること | 実際の poll 順、HTTP、SQLite の保存結果 |
| service とフェイク | `ReadingService` と制御可能な Adapter | 並行開始、完了順と入力順、失敗後の継続、親 Future 破棄後の状態 | SQL、transaction、Axum rejection |
| SQLite Adapter | 実 SQLite、SQL、行変換 | 条件付き更新、状態とメモの commit・rollback | HTTP の status・JSON、service の整列 |
| Router と実 SQLite | routing、extractor、handler、service、DB、応答変換 | 入力の受理・拒否、項目結果、再取得できる保存状態 | TCP 設定、任意の scheduler や障害 |
| 実アプリ | TCP を含む実際の server 経路 | 実行した要求の応答と保存状態 | 実行しなかった障害や将来の全実行 |
| mdBook とブラウザ | 目次、章移動、抜粋、図、問題と解答、検索表示 | 生成物が読め、参照先へ到達できること | 読者が問いに答えられること自体 |
| 読解レビュー | 本文と参照コードで各章の問いへ答えられるか | 説明と根拠の不足 | 任意の読者の理解、実行時安全性 |

service のテストは実時間の短さで並行性を推測しません。フェイクの待機点で二冊とも開始したことを確認してから解放します。完了順や親 Future の破棄も同じ制御点で再現します。

SQLite の rollback テストは、メモ INSERT を拒否する trigger で状態更新後の失敗を決定的に作り、再取得した状態が読書中、メモが空であることを観測します。すべての DB 障害を網羅するわけではありません。

Router の `oneshot` は TCP を開きませんが、実際の routing から SQLite と応答変換まで通ります。実アプリ確認はこれに TCP の待ち受けと実ファイル DB の経路を加えます。

テストは内部呼び出し回数や偶然のエラー文言ではなく、公開された結果と再取得できる保存状態を固定します。エラー本文が HTTP 契約に含まれる場合は Router で確認し、service の単体テストではエラー分類を確認します。

## 完成形の統合確認

実ファイル DB を隔離したディレクトリに作り、`cargo run` で起動した実アプリへ TCP 経由で要求した結果を確認しました。

| 実行した経路 | 応答 | 再取得した保存状態 |
| --- | --- | --- |
| 読書中の 2 冊を入力順 `3, 1` で読了記録 | `200 OK`。同じ入力順で 2 件とも `completed` | 2 冊とも読了し、それぞれのメモが 1 件ずつ残る |
| 未検出、未読、読書中の 3 冊を同じ要求に含める | `200 OK`。入力順で `not_found`、`conflict`、`completed` | 未読の本は変更なし。成功した本だけが読了し、メモが残る |
| 正しい項目の後ろに空本文を置く | `400 Bad Request` と `validation_error` | 両方とも読書中のままで、メモは残らない |
| 一冊だけ `notes` の INSERT を拒否する trigger を置き、正常な別の本と同じ要求に含める | `200 OK`。入力順で `internal_error`、`completed` | 失敗した本は rollback され、読書中のままでメモなし。別の本は読了し、メモが残る |

生成した教材はブラウザで開き、導入と 13 章が目次に並ぶこと、前後の章へ移動できることを確認しました。全章で「問い」「読む場所と順序」「確認」「解答」と少なくとも 1 つのコード抜粋が表示され、Mermaid を含む章では図が SVG として描画されました。教材が日本語検索の代わりとして案内する識別子も確認し、`BookRepository` は「`BookRepository` の契約」、`NoteBody` は「借用して検査し、所有して渡す」、`FuturesUnordered` は「完了順と入力順を分ける」、`record_reading_completion` は複数章の「読む場所と順序」へ到達しました。日本語検索は分かち書きに制約があるため、任意の日本語で対象へ到達できることまでは保証しません。

読解レビューでは、導入と各章の問いについて、同じ章の解説、解答、指定された参照コードから理由をたどれることを確認しました。これは説明と根拠がそろっていることの確認であり、任意の読者が理解できることや、未実行の経路が正しいことの証明ではありません。

実アプリでは、HTTP 接続を意図した時点で切断して親 Future の破棄時点を固定する確認は行っていません。この経路は制御可能なフェイクによる service テストで観測します。また、利用する外部サービスはなく、任意の scheduler、任意の DB 障害、将来の全実行は未確認です。

## 別案との比較

### Router テストだけで済ませる

広い経路は通りますが、競合の発生位置、子 Future の解放順、親 Future の破棄を決定的に制御できません。必要な場合だけ低い Seam を使います。

### 自動テスト成功を教材の理解の証明にする

コードの振る舞いは確認できますが、本文と参照コードだけで学習者が問いへ答えられるかは分かりません。読解レビューを別に行います。

### mdBook build 成功を表示確認にする

構文上の生成は確認できますが、章移動、図、抜粋、検索の実際の表示は分かりません。ブラウザで生成物を確認します。

## 確認

1. service の並行性テストが実時間を使わない理由は何ですか。
2. Router テストと実アプリ確認の範囲はどう違いますか。
3. rollback テスト一件から、すべての SQLite 障害を保証できますか。
4. mdBook build とブラウザ確認を分ける理由は何ですか。
5. 自動テストと読解レビューは、何を別々に保証しますか。

## 解答

1. 環境速度や scheduler の偶然を避け、複数処理が解放前に開始済みという状態を直接観測するためです。
2. Router テストは TCP を使わず routing 以降を通し、実アプリは TCP の待ち受けと実ファイル DB も含めます。
3. できません。注入した失敗で rollback することは示しますが、未実行の障害や任意の時点は網羅しません。
4. 生成成功だけでは、利用者が見るナビゲーション、図、抜粋、検索結果を確認できないためです。
5. 自動テストは実行した契約、読解レビューは本文と参照コードから問いへ答えられる説明の充足を確認します。

## 読了時の総合確認

一括読了記録について、入力の所有権、型状態と実行時検査、一冊の原子性、冊子間の部分成功、Adapter の具体化、Future の所有関係、結果順、失敗後と親終了後の状態を、参照コードを根拠に説明してください。説明できない箇所があれば、目次から対応する章へ戻ります。
